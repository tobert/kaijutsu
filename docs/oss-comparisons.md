# OSS prompt and context comparisons

This is a growing source dossier for Kaijutsu's prompts, prompt construction,
and conversation continuity. It records mechanisms to learn from, where their
assumptions differ from ours, and experiments that could justify a change.
It is not a ranking of agents or a specification for replacing rc.

Amy, 2026-09-10: “we'll build a dossier first in docs/oss-comparisons.md that
can build up over time.” The first pass emphasizes omp's prompting and setup,
then compaction and other auxiliary prompts. No shipped Kaijutsu prompts
were changed as part of this pass.

For complete before/after Kaijutsu prompt bodies, open the
[side-by-side comparison](prompt-comparison.html). It reads the pinned old
baseline and current seeds, with optional shared-base inclusion and wording
diffs. [Prompt configuration](prompts.md) owns the implemented contract.
This is not a complete provider-request capture. Upstream prompt text remains
in the pinned source links below; this dossier does not reproduce every template.

## Kaijutsu's starting point

This section describes the inspected pre-change baseline. See `docs/prompts.md`
for the implemented behavior after the review.

At the inspected baseline, the base was [assets/defaults/system.md](https://github.com/tobert/kaijutsu/blob/208cd9db91c0dfa3fbdb4623a77ffe2a447ddaf5/assets/defaults/system.md): a short
shared-workspace stance about peers, accountability, visible failures, and
improvement. The runtime builder joins the loaded base, eligible rc-derived
`Role::System` / `BlockKind::Text` sections, and a per-call `<situation>` tail
containing context identity/state, model, and tool names. Other block kinds do
not become system instructions merely because their role is System.
See [system_prompt.rs](https://github.com/tobert/kaijutsu/blob/208cd9db91c0dfa3fbdb4623a77ffe2a447ddaf5/crates/kaijutsu-kernel/src/llm/system_prompt.rs).

rc already supplies composition through ordinary files and symlinks. The
shared kaish primer is generated by `kj kaish primer`, not copied into each
stance. Date, memory recall, and character handoff material use Notification
blocks to avoid making their changing text part of the cached system prompt.
See [the primer script](https://github.com/tobert/kaijutsu/blob/208cd9db91c0dfa3fbdb4623a77ffe2a447ddaf5/assets/defaults/rc/lib/create/S05-kaish.kai),
[recall](https://github.com/tobert/kaijutsu/blob/208cd9db91c0dfa3fbdb4623a77ffe2a447ddaf5/assets/defaults/rc/coder/create/S15-recall.kai), and
[handoff](https://github.com/tobert/kaijutsu/blob/208cd9db91c0dfa3fbdb4623a77ffe2a447ddaf5/assets/defaults/rc/coder/create/S16-handoff.kai).

`kj context prompt` already previews assembled system text through the shared
builder. Reuse that seam for inspection; a new prompt framework is not a
prerequisite. It is a system-text preview, not a complete capture of provider
messages, schemas, cache markers, and auxiliary requests.
See [context.rs](https://github.com/tobert/kaijutsu/blob/208cd9db91c0dfa3fbdb4623a77ffe2a447ddaf5/crates/kaijutsu-kernel/src/kj/context.rs).

Project-instruction discovery is already an open item in `docs/issues.md`,
"MCP subsystem — audit follow-ups". The builder does not crawl for AGENTS.md.
The other agents' discovery and scope rules are therefore a setup comparison
to revisit here, not a behavior Kaijutsu should claim in its base prompt today.

| `coder` | Explicit coding role; change/test/report; focused and guided model branches | Contains reusable collaboration guidance, but is not currently generic |

[assistant stance](https://github.com/tobert/kaijutsu/blob/208cd9db91c0dfa3fbdb4623a77ffe2a447ddaf5/assets/defaults/rc/assistant/create/S00-stance.kai),
[default rc](https://github.com/tobert/kaijutsu/blob/208cd9db91c0dfa3fbdb4623a77ffe2a447ddaf5/assets/defaults/rc/default), and `docs/character.md`.

**At this baseline, compaction is a compact fork.** `kj fork --compact` calls the shared
distiller and seeds a new context with a Distill drift block that references
the source context. The parent remains available. The distillation instruction
asks for a briefing under 500 words; the formatter sends role/kind-labeled
text, keeping only the first 2,000 bytes of each nonempty block at a UTF-8
boundary. The truncation marker names the original size, but the transcript
does not include each block's identifier. This path does not select and copy
a verbatim recent-message tail into the child.
See [fork.rs](https://github.com/tobert/kaijutsu/blob/208cd9db91c0dfa3fbdb4623a77ffe2a447ddaf5/crates/kaijutsu-kernel/src/kj/fork.rs),
[distillation.md](https://github.com/tobert/kaijutsu/blob/208cd9db91c0dfa3fbdb4623a77ffe2a447ddaf5/assets/defaults/prompts/distillation.md), and
[build_distillation_prompt](https://github.com/tobert/kaijutsu/blob/208cd9db91c0dfa3fbdb4623a77ffe2a447ddaf5/crates/kaijutsu-kernel/src/drift.rs).

That loss happens before the summarizer sees the content. Wording alone cannot
recover a decision at the end of a long block. Also distinguish a brief sent
by drift from a handoff intended to resume an entire task: both currently use
the same distillation helper, but they need different retention criteria.

## omp: prompting and setup

### How the prompt is built

The useful unit of study is `buildSystemPrompt()` plus the SDK's inputs and
the selected tool roster. The [default template][omp-template] is only one
part of the request. [The builder][omp-assembly] resolves project context,
skills, rules, append/custom text, personality, environment, model-related
options, and tool metadata before rendering bundled templates.

| Input | How it reaches the model | Lesson for Kaijutsu |
|---|---|---|
| Default instruction template | Role, engineering, tool policy, workflow, delivery | Keep behavior explicit, but inspect the cost and conflicts of accumulated rules |
| Personality | Selected preset or user override; omitted for `none` | Separate voice from task procedure and tool contracts |
| Tool metadata | Compact callable-name list or full rendered inventory | Derive names and instructions from the effective roster |
| Skills | Name/description catalog, full content fetched through `skill://` | Discovery belongs in the prompt; full procedure can be loaded when needed |
| Rules | Always-apply bodies plus a catalog of domain rules | Distinguish standing guidance from guidance that needs a task trigger |
| Project footer | Context files, deeper-directory pointers, workstation and workspace facts | Give observations a source and scope |
| Date/cwd reminder | First user turn of each provider request | Avoid varying bytes ahead of a reusable prompt/schema prefix |
| Conditional additions | Computer guidance, active nested repository, memory/MCP guidance | Inspect the final composition, not just the primary template |

Tool references use effective wire names. Tools available only through a
bridge/device are distinguished from top-level callable definitions. Skills
are advertised only when `read` is available; hidden skills are omitted from
the catalog. Always-apply rules and context files have deduplication logic.
These are observable assembly properties worth testing independently of model
behavior. See [inventory tests][omp-inventory-tests] and
[context deduplication tests][omp-context-tests]. These tests were read, not run.

`inlineToolDescriptors` defaults to `auto`: the setting describes inlining for
Gemini and schema-hosted descriptions otherwise. In inline mode, descriptions
are stripped from provider schemas so the descriptive text is sent once.
With native calling and no inlining, the prompt uses the shorter tool list.
This is a provider representation decision, not evidence that every model
benefits from a longer tool tutorial. See [settings schema][omp-settings-schema].

### Setup and override semantics

The [customization contract][omp-customization] distinguishes three actions:

| Mechanism | Scope |
|---|---|
| `APPEND_SYSTEM.md` / `--append-system-prompt` | Retains default instructions and adds text |
| `SYSTEM.md` / `--system-prompt` | Replaces the default instruction template while retaining generated context, skills, rules and the project footer |
| SDK `systemPrompt` | Can replace all rendered provider-facing system blocks |

This distinction is easy to miss: a CLI “system prompt” replacement is not
the SDK's complete replacement. Append placement also differs between the
default and custom templates. User files are inserted as literal text;
Handlebars inside them is not recursively evaluated.

Prompt-file discovery is project-first, then user-level. Within each scope,
the config bases are `.omp`, `.claude`, `.codex`, `.gemini`. It checks the
launch cwd and does not walk ancestors for these prompt override files.
Project context discovery is a separate mechanism. A profile changes the
native user directory. `PERSONALITY.md` uses only the native agent directory;
`TITLE_SYSTEM.md` separately controls automatic naming. All of these details
come from [the customization contract][omp-customization].

[Settings precedence][omp-settings] is built-in defaults → global config →
project config → explicit CLI config overlays → runtime overrides. The native
global file is `~/.omp/agent/config.yml`; project configuration includes
`.omp/config.yml`. Model roles such as `smol`, `slow`, and `plan` are configured
separately. Naming, memory extraction, and other auxiliary calls can therefore
have different model choices from the main coding turn.

**Proposal:** borrow the clear vocabulary for append, replacement, discovery,
and scope. Keep Kaijutsu's ordinary host files, rc lifecycle, and single kernel
ownership. Copying omp's cross-product config search or template engine would
add machinery without establishing a need here.

### What its behavioral prompt has learned—and where it conflicts

The default template gives concrete recovery guidance: reread after a failed
edit or changed file; ground tool and test claims in observed results; resolve
prerequisites; retain ownership of task decomposition; assign independently
runnable work; and keep working until the requested deliverable is complete.
Tool-specific instructions are conditional on tool availability.

Several choices should not be imported as Kaijutsu policy:

- It treats user-reported observations as ground truth and forbids confirming
  them. Respecting a report is useful; forbidding a reproducer conflicts with
  our feedback loop and contributing-factors analysis.
- It strongly discourages new permanent tests except for uncertain edges or
  user requests. Keep our TDD posture and tests that fail on plausible mistakes.
- It forbids discussing budgets in its critical instructions. Amy's model
  spend posture calls for visible, deliberate cost choices.
- It defaults to broad clean cutovers. That fits Kaijutsu's learning space,
  but not automatically kaish/aider-like public compatibility promises.
- Its XML convention assumes special tags in user messages are system-authored
  because user content was sanitized. A textual tag is not provenance in
  Kaijutsu; preserve kernel-authored source and role information.
- It routes many operations away from shell to specialized tools. Kaijutsu's
  host execution owner remains kaish; transfer tool-use clarity, not omp's
  dispatch policy.

These are differences visible in [the prompt][omp-template], not claims that
omp performs badly. The large number of absolute rules is itself a reason to
evaluate rendered combinations for contradiction before borrowing prose.

### Auxiliary prompts are part of the behavior

| Prompt family | Concrete function | Transfer candidate |
|---|---|---|
| [Date/cwd][omp-date] | Supplies fresh request facts outside the system prefix | Keep runtime observations out of stable instruction text |
| [Auto-continue][omp-continue] | Rechecks latest intent against retained messages and declines to invent more work | A handoff must preserve intent changes and completion |
| [Tool-loop redirect][omp-loop] | Names the repeated tool, arguments, count, and last result | Detect repetition mechanically, then provide specific recovery guidance |
| [Memory extraction][omp-memory] | Extracts explicit durable facts; omits one-off plans and inferred facts | Distinguish long-term memory from task handoff |
| [Title customization][omp-customization] | Separate prompt and normalized, bounded output | Auxiliary tasks need their own input/output contracts and model routing |
| [Summary, update, turn-prefix and branch prompts][omp-compaction-dir] | Different instructions for different continuity operations | One generic summarization prompt need not serve every transfer |

A repeated-call reminder is useful only if its detector identifies a real
loop. It must not block legitimate polling whose arguments stay the same
while external state changes. Kaijutsu can test that distinction without an
LLM before evaluating the recovery wording.

### Compaction, retained history, and recoverable content

omp persists compaction entries with a summary, a retained-history boundary,
token accounting, and optional structured preservation data. Branch summaries
are separate entries used during tree navigation. On context rebuild, the
latest compaction and retained entries become model input; summary wrappers
become user-context messages. See [compaction documentation][omp-compaction]
and [implementation][omp-compaction-code].

The summary instructions preserve goals, constraints, completed/in-progress/
blocked work, decisions, next steps, exact references, and pending questions.
The update prompt revises previous progress and questions; the turn-prefix
prompt explains the retained suffix. This is more targeted than merely
asking for a shorter transcript. Its tension between preserving all previous
information and removing irrelevant material should be tested over repeated
compactions, not resolved by adding another absolute instruction.

At this revision, defaults include a 20,000-token recent tail, a 16,384-token
base reserve, mid-turn maintenance, and automatic continuation. Reserve
calculation is also proportional to the model window and handles small
windows; these constants are not a universal threshold formula. The summary
output has a 16,384-token ceiling, explicitly preventing large windows from
authorizing a near-transcript-sized output. See [the implementation][omp-compaction-code].

The default method preference is `remote → snapcompact → handoff → shake →
soft`, with availability/recovery conditions determining which runs. Overflow
and ordinary pressure have different paths. In particular, an overflowing
request cannot safely be reused for the same full-input handoff call.
See [method selection][omp-methods] and [maintenance contract][omp-compaction].

Two techniques deserve separate experiments:

- **Shake:** replaces eligible heavy content with recoverable artifact
  references, protecting recent material and requiring useful savings. This
  makes deterministic reduction a distinct operation from LLM summarization.
- **Experimental notes-backed windows:** a bounded 16,384-byte notebook,
  complete recent tool units, and searchable original history support rollover
  without a summarization call. It is off by default and requires the notes,
  rollover, read, and grep tools. The model still has to maintain useful notes.

Both are described in [the compaction contract][omp-compaction]. They fit our
durable-context/limited-conversation distinction better than discarding the
source. We already have documents, block references, fork, and handoff logs;
assess what these can express before adding notebook machinery.

**Snapcompact** renders bounded serialized history into images for a vision
model to read. This is deterministic archival processing, but not a lossless
semantic channel: serialization can truncate content, and recovery depends on
vision behavior and provider representation. The repo carries model-specific
experiments; they were not reproduced here. Treat it as a research technique,
not a base dependency for our DeepSeek-heavy workflow. See
[snapcompact implementation][omp-snapcompact].

## DeepSeek Harness: prompt contribution and cache-aware summaries

[System-prompt assembly][dsh-assembly] owns ordered sections, variables,
runtime contexts, and tool schemas. Section order is numeric, then by name.
Agent-scoped definitions can shadow global definitions; duplicates within a
layer, unresolved variables, and multiple effective complete prompts fail
assembly. A `complete` section replaces prompt sections while tool/context
assembly still runs. [Persona][dsh-persona] uses that same scoped API.

Its strongest distinction is `PromptSection` versus `PromptContext`. Dynamic
contexts become sourced user-role snapshots after retained history when they
change or need restoration after compaction. System updates can also be
appended in history when the prepared route explicitly supports that mode;
otherwise the system head is updated. This is a provider capability, not a
portable assumption about all chat APIs. See [the subsystem contract][dsh-system-doc].

Tool restrictions do not automatically remove independently registered prompt
guidance. That caveat matters: a well-defined contribution API alone does not
guarantee that every advertised operation is callable. omp's roster-dependent
rendering and DeepSeek Harness's strict registration catch different mistakes.

The [compaction summarizer][dsh-summarizer] replays the conversation's own
system/tools/message prefix and appends a compaction directive. This preserves
the opportunity for prefix-cache reuse on the same route, rather than always
starting with an unrelated summarizer system prompt. The requested output
captures evolving intent, corrections, exact references, pending jobs, current
work, and the next action. Previous checkpoints are revised, not copied
verbatim. Empty text summaries and unsuccessful finish conditions fail.

[Compaction][dsh-compaction] is an optional service with explicit pressure and
overflow triggers. The basic backend can first invoke deterministic tool-result
pruning and remeasure. Selected boundaries preserve tool-call/result pairing;
a long turn can be reduced at a closed step rather than waiting for the whole
turn to finish. Start/summary/end records and selected source sequences make
the operation inspectable. Manual attempts revalidate their selected span so
unrelated injected context can survive while summarization is pending.

**Proposal:** test cache-reusing same-model distillation against explicit
cheap-model distillation. Compare total billed input/output and continuation
quality; a cheaper model with a cold cache is not automatically the cheaper
operation. Preserve our explicit provider/model choice and cost visibility.
Do not copy its in-place conversation replacement into Kaijutsu without a
design discussion: our conversation is append-only between hydrate boundaries.

## Codex: model instructions and context reconstruction

The checkout contains several historical model prompt files. No one such file
establishes the active prompt. [Model configuration][codex-models] applies
instruction overrides and personality handling to model information, while
[initial context assembly][codex-session] gathers typed context fragments from
world state and extensions. [Base-instruction fragments][codex-base] and
developer instructions have explicit roles; project/user context is separately
represented. The assembled request is the object to compare.

[The local checkpoint prompt][codex-compact-prompt] is short: progress,
decisions, constraints/preferences, next steps, and critical references.
[Its continuation prefix][codex-compact-prefix] tells the next model to build
on prior work. The more consequential contract lives in
[compact.rs][codex-compact]: pre-turn/manual compaction leaves initial context
for the next normal turn to inject, whereas mid-turn compaction explicitly
places it before the last real user message. Live and persisted replacement
history must receive the same item identities.

The checkout also has [remote compaction][codex-remote] and extensive
[request/history-shape tests][codex-compact-tests]. The local summary prompt
does not disclose the implementation of a hosted compaction service. In
particular, do not describe provider-native compaction as a portable text
summary solely because both operations are called compaction.

**Proposal:** test reconstruction with absent, stale, and newly changed runtime
facts. Compare exact provider-facing roles and tool pairing as well as the
summary's prose. Retain the distinction between portable Kaijutsu facts and a
provider's private continuation representation.

## Secondary comparisons

### Crush

[Prompt construction][crush-builder] uses Go templates with provider/model,
workspace/platform/date/git facts, context files, and a skills catalog.
[The coder template][crush-coder] gives a concrete read/edit/verify sequence
and exact-edit recovery advice. It also accumulates conflicting pressure:
limited section reads versus reading the entire file, asking only in specific
cases versus an initial prohibition on questions, and tests after each
modification. These are reasons to inspect complete rendered combinations.

[The summary prompt][crush-summary] asks for current state, files, successful
and failed commands, rationale, and exact next steps. Its instruction to use
unlimited length is a poor fit for bounded continuation. Borrow the fields
and failed-attempt evidence; evaluate a budget and retention policy separately.

### Goose

[The base prompt][goose-system] is explicitly general-purpose. Active
extensions contribute their own instructions, and the prompt warns that
historical extensions may no longer be active. [PromptManager][goose-builder]
sorts extension information for stable ordering and adds project hints and
other extras. This is useful evidence that a generic role can coexist with
task-specific tool guidance. Its template-error path falls back to a minimal
identity string; Kaijutsu should preserve an observable assembly failure.

[Compaction][goose-compact] distinguishes manual compaction from automatic
continuation, preserves the relevant real user message on the automatic path,
and excludes agent-added turn context from that selection. Its
[summary renderer][goose-summary] has fields for user intent, files, errors,
pending work, and next steps. **Proposal:** distinguish actual user steering
from notifications, drift, and other injected material in continuity tests.

### Hermes Agent

[Prompt assembly][hermes-system] separates stable, context, and volatile
parts: identity/guidance; workspace and session guidance; then skills, memory,
profile, and timestamp. The assembled prompt is cached for the session and
rebuilt after compression. This trades freshness for cache stability explicitly;
it is not the same lifecycle as rereading every input on every turn.

[The compressor][hermes-compact] has unusually useful failure evidence:
summary-end markers address weak models answering historical requests or
repeating the summary; strict chat-template alternation treats tool messages
differently from ordinary user/assistant turns; persistence markers must be
removed from copied messages or a new session can skip saving them. These
comments describe concrete failure mechanisms, not just prompt preferences.

Its wrapper goes too far for our steering contract: it says historical
requests were already addressed and only the latest message defines the task.
A status question during active work should not cancel that work in Kaijutsu.
Borrow explicit historical boundaries, but preserve unresolved goals and
distinguish a correction/cancellation from an ordinary follow-up.

### Aider

[Editblock prompts][aider-edit] teach the SEARCH/REPLACE protocol through
worked user/assistant examples. [Message construction][aider-builder] keeps
system instructions, examples, prior history, repository map, read-only files,
editable files, current messages, and reminders as separate chunks. This is
useful for our kaish primer: correct examples should teach the actual tool
contract, with current state distinguishable from earlier file snapshots.

[Architect instructions][aider-architect] explicitly prepare a complete brief
for an editor that relies on it. That is a focused split of responsibilities,
not an argument for delegation on every task. [ChatSummary][aider-history]
retains a recent tail when possible and recursively summarizes older messages
under a token budget; its class default is 1,024 tokens, not a universal
runtime setting. Its alternating text-chat and user-managed file selection
assumptions do not directly match Kaijutsu's multi-writer context or kaish tools.

## Kaibo: evidence gathering and review

Kaibo supplies a useful neighboring design: grounded, read-only consultation
with an explorer and synthesis agent. Its prompt composition has one owner,
`resolve_phase_preamble`, with complete role overrides and separate project
orientation/house-rule layers. Tool-bearing phases share generated kaish
guidance; oneshot and offline synthesis explicitly lack project tools.

The [complete rendered prompt resource](kaibo-prompts-current.md) preserves
the current text. The [Kaibo implementation report](kaibo-prompt-proposal.md)
maps the prompt contracts back into its roles, with proposed evidence and review
passages, auxiliary-prompt changes, and tests. That report pins the source
and [explorer PR #183](https://github.com/tobert/kaibo/pull/183), which names
whether an explorer reports to the caller or a synthesis agent. These are
distinct reader needs even when the reading procedure is shared.

Lessons for Kaijutsu: prompt previews should disclose the layers they omit;
evidence status should survive a handoff; a source citation needs an explanation
of how it supports the claim; and forced completion should report incomplete
evidence honestly. Kaibo already keeps tool definitions but disables new calls
for a final recovery turn. That is a runtime mechanism alongside its prompt.
Its question/answer session replay and recovery transcript are not semantic
compaction in the inspected paths.

The arriving DeepSeek and GLM reviews also supplied cases where a finding
confused draft behavior with shipped behavior or inferred a hook's effect
without following its implementation. Selected claims were checked locally
and recorded in the implementation report. Those cases motivate an experiment;
they do not establish that any model or prompt is generally better.

## Polytoken: documented composition

**Documented:** a facet controls prompt framing, tools, skills, optional model
pinning, and presentation. The body is the complete framing; including the
shipped base is explicit through `transclude("polytoken://system_prompts/facet.md")`.
Shipped `plan`, `execute`, and `orchestrate` facets add to that base. Project
facets replace global/shipped definitions of the same name. Switching facets
changes the system prefix and can lose cache reuse while preserving the
conversation. See [Facets](https://docs.polytoken.dev/harness-engineering/facets/).

**Documented:** MiniJinja templates can test tool, skill, MCP, and model
availability. Unknown variables fail rendering. Static `@file` inclusion
differs from render-time `transclude`; skills opt into templating while facet
and subagent bodies always use it. See
[Templating](https://docs.polytoken.dev/harness-engineering/templating/).

**Documented:** shipped prompts and definitions can be inspected with
`polytoken vfs ls 'polytoken://system_prompts'` and
`polytoken vfs cat 'polytoken://system_prompts/facet.md'`.
These commands have not been run here. They provide a concrete next inspection
path if source is unavailable, rather than inferring shipped prompt text from
customization examples. See
[The Polytoken VFS](https://docs.polytoken.dev/extending-polytoken/polytoken-vfs/).

**Documented:** `/compact` records a summary event and supports guidance;
automatic compaction responds to context pressure, while todos survive in the
session. Skill chains are deduplicated, capped at 64 KiB, and cached so their
bodies can be restored after compaction. These are useful task-state and
procedure-retention ideas, but exact selection, failure behavior, and summary
instructions remain unverified. See
[Sessions](https://docs.polytoken.dev/using-polytoken/sessions/) and
[Skills](https://docs.polytoken.dev/harness-engineering/skills/).

## Direction for base, coder, and general-purpose contexts

**Implemented composition decision:** Amy chose ordinary rc
symlinks to opt each context type into shared prose, with no mandatory base
prompt. This supersedes a larger universal base and a smaller mandatory
stance alike. See [prompt configuration](prompts.md).

The shipped seeds strengthen the optional common contract and make
`default` useful for general work without adding a new context type. Coder
keeps a specific coding procedure. An extra type earns its existence when a
different loadout, lifecycle, or sustained role needs a name—not just a copy
of the same stance with “coding” removed.

| Layer | Responsibility | Keep elsewhere |
|---|---|---|
| Optional shared rc body | Work as peers; preserve the user's objective and corrections; ground claims; disclose uncertainty/failure; finish authorized work; ask when a decision needs the user | Automatic inclusion in every type, coding sequence, fleet schedule, provider-specific instructions |
| `default` | Research, explanation, writing, planning and tool work as the request requires; report sources and remaining uncertainty | An automatic coding workflow or coordinator duties |
| `coder` | Read relevant code; write a failing behavior test; implement; verify; report; preserve scope and existing conventions | Repeated generic collaboration rules |
| Character | Who is working, personal commitments, memory and handoff sources | Universal task procedure |
| Tool help/schema | Actual syntax, output limits, errors and recovery; examples | A second handwritten copy in each stance |
| Runtime context | Current model/loadout/cwd, source-stamped observations, pending external work | Stable persona prose |
| Continuity operation | Accepted intent, progress, decisions, open questions, exact recovery references, and retained recent material | An unsupported claim that every old request is complete |

There is overlap between the present assistant stance and a character's
durable duties. Resolve that against `docs/character.md` before renaming or
moving it. `docs/conversation-session.md` remains the contract for hydrate
boundaries; neither a mode switch nor a summary should quietly rewrite the
live conversation.

The existing coder model-name branches deserve measurement rather than a
larger pattern list. They select a stance at lifecycle execution; per-call
model facts can change later. Test a model change explicitly. A model-family
workaround should name observed behavior, its test case, and a removal
condition. “Frontier gets less procedure” is a hypothesis, not a capability
guarantee derived from a model's name.

## Candidate experiments and acceptance evidence

Do these as bounded changes after the dossier discussion. Use DeepSeek via
the DeepSeek API for bulk model trials; record the exact model and route.
Use cheap comparison models deliberately. Source review does not authorize
an open-ended benchmark bill.

| Priority | Experiment | Evidence that could reject it |
|---|---|---|
| 1 | Capture complete rendered requests for base/default/coder and both coder branches | Missing/duplicated guidance, unavailable advertised tools, unstable schema ordering, unexpected prefix changes |
| 1 | Add a continuation-specific compact-fork fixture set | Loses unresolved request, user correction, pending question, failed test, current path, source pointer, or necessary recent tool result |
| 1 | Replace unrecoverable 2,000-byte cuts with bounded, cited reduction | Tail decision or error still unreachable; total input unbounded; tool pairing broken; Unicode damaged |
| 2 | Compare common base + coding-specific stance against current coder | More scope drift, unnecessary questions, unsupported success claims, or worse behavior on a genuine bug-fix task |
| 2 | Run noncoding tasks under `default` | Forces editing/tests onto writing or explanation, cannot select relevant tools, or imports fleet duties |
| 2 | Compare same-model cache reuse with explicit cheap distillation | Higher total cost/latency without better continuation; hidden provider change |
| 3 | Recover heavy tool output through existing context/block references | Repeated reading costs more than retention, stale references, or unavailable source after restart |
| 3 | Test a detected repetition reminder | Blocks legitimate polling or permits the same failed action indefinitely |

Continuity fixtures should include a status question that leaves the original
task active; explicit cancellation; an unanswered question; a correction near
the end of a long block; two successive compactions; an outstanding background
job; interleaved writers; a restart; and a changed model/loadout. Verify that
the new context receives its intended base, stance and tool guidance too.
Distinguish current instructions from historical quotations and summaries.

Measure system text and tool-schema cost separately, using the target
tokenizer or actual provider usage. Capture total/cached input, output, latency,
and continuation behavior. Raw source length is not a token measurement.
Deterministic assembly tests should fail before the fix; model trials should
compare variants on the same tasks. No byte-count target or quality threshold
has been selected in this pass.

## Prompt review lessons

DeepSeek V4 Flash and GLM 5.3 reviewed the draft design through Kaibo; Claude
Code reviewed the same prompt work afterward, pinning its source citations to
`14589559`. Their findings were checked against the relevant code and original
answers before adoption. The original review synthesis and plans remain in git
history; raw answers are retained privately in
`~/exomemory/kaijutsu/prompt-review-2026-09-10/`. These were design reviews,
not comparative measurements of model behavior.

The strongest common findings concerned what the summarizer actually received:
excluded and draft blocks leaked into it, ordinary system instructions became
source text, each block lost its tail after 2000 bytes, identifiers were absent,
and total input was unbounded. Prompt wording alone could repair none of those
conditions. The implementation shares hydration eligibility, adds source/tool
metadata, retains bounded complete turn groups, and gives briefing and
continuation separate host-file instructions and context-scoped length controls.
See `docs/prompts.md` for the defaults and failure behavior.

Several findings needed correction:

- GLM inferred that the fork lifecycle restored coder stance. Inspecting the
  actual fork scripts showed only cache and datetime hooks; creation owned the
  stance. Compact forks now retain the source's chosen instruction blocks.
- DeepSeek compared proposed base text with old coder text when reporting
  duplication, and requested steering language already present in the handoff
  draft. Review the exact versions and read the whole applicable contract.
- A local review summary claimed a `kj drift push --focus` precedent. The real
  interface is trailing positional text on `kj drift pull`.
- An embedded checkout HEAD made HTML regeneration self-changing after every
  commit. The comparison now separates a pinned historical baseline from input
  hashes that determine the current render.

Claude identified a conflict between universal working guidance and the
musician's ABC-only, deadline-driven output. Amy then removed the premise of a
universal base: “I don't think kaijutsu should force any one prompt into every
context type.” Ordinary rc symlinks let each type choose shared instructions.
That decision supersedes both the larger universal draft and the proposed
smaller mandatory base. The optional shared body retains
`頑張（がんば）って！` at Amy's request.

The implementation review ran on Kaibo's `crusoe` cast, configured with
DeepSeek V4 Flash as explorer and GLM 5.3 as synthesis, against `94da5410`
and `08ffcbca`. It
confirmed the main composition, budget, provenance, and continuation contracts.
Two findings were fixed: the guide had incorrectly deferred stored instruction
edits until hydration, and live/preview assembly silently used no instructions
when a block read failed. The shared reader now preserves read errors; a
missing-document regression reproduces the old failure, while an existing empty
context remains valid. Instruction edits and exclusions are read before each
turn. This is distinct from ordinary history hydration.

The remaining review observations were checked and scoped: source metadata is
outside the block-version guard; late fork initialization failures can leave
partial state (not always an orphan document, as the original report claimed);
orphan tool results remain durable but are omitted by conversation repair; and
Pending status is not swept with Running/Waiting. Open fork consistency and
queued-work questions are in `docs/issues.md`; current edge behavior is in
`docs/prompts.md`. The 4096-token one-shot cap is documented only for the
adapters that actually request it. Raw review output remains in the private
review archive. These are source-level conclusions, not model-effectiveness
measurements or a live deployment check.

The [Kaibo proposal](kaibo-prompt-proposal.md) uses these checked review mistakes
as examples for evidence status, grounding, and handoff tests. A cited claim
still needs an explanation of how its source establishes the behavior.
